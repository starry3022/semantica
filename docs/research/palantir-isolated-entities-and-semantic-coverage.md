# Palantir：孤立实体、类别建模与语义覆盖

调研日期：2026-09-21。范围：Palantir Foundry / AIP 官方公开文档，以及当前
`candidate_profile_v3.json` 中文材料的本地 DeepSeek 产物。

本次先复用 [本体关系与证据溯源调研](palantir-provenance-relationships.md)，
再补查对象/属性建模、关系的数据来源、Vertex 遍历和 AIP 评估机制。

## 问题

Explorer 中“办公设备”“软件服务”“其他业务资源”为何独立存在？它们是否与采购申请
没有关系？Palantir 如何处理同类的类别、适用条件及缺少可遍历连接的问题？

## 本地已确认事实

检查对象为 `.local/candidate-profile-v3-provenance-v4/` 及 `127.0.0.1:8020` 的图 API。
原文第一章第 10–11 行描述：员工因业务需要采购这些资源时，应提前提交采购申请。

| 层级 | 核查结果 |
| --- | --- |
| 实体抽取 | 三个名词被抽为 `ResourceType` 候选实体，含原文引用；不是某台实际设备或某笔实际购买记录。 |
| 原始 LLM 关系响应 | `extraction.json` 保存 21 条关系，三个资源实体均未作为任何业务关系端点。 |
| 关系表达 | 存在 `员工 → submitsAdvance → 采购申请`，三个资源名称只出现在这条断言的 `condition` 字符串里。 |
| 归一化结果 | `facts.json` 同样为 21 条关系；`extraction-issues.json` 为空，未见这些连接因端点或格式错误被丢弃。 |
| 实时 Explorer 图 | 每个资源节点只有 `rdf:type → ResourceType` 和 `hasEvidence → 引用片段`。两者在默认业务视图隐藏，因此看起来孤立。 |
| 既有提示词 | `relationship-prompt.txt` 已要求保留类别/情形到请求或活动的适用范围关系，以及多参与方动作；本次响应仍没有覆盖这些关联。 |
| 现有校验 | `_normalize_relations` 校验端点身份、重复项、证据与字段等，不判断每个原文语义是否已完整结构化。校验通过不能证明没有语义遗漏。 |

共有 9 个实体没有业务连线：办公设备、软件服务、其他业务资源、紧急采购授权、生产故障、
客户重大事故、其他紧急业务情况、紧急采购、以及类型为 `ProcurementApprovalProcess`
的“采购审批”。这是一份待复核清单，不等同于“必须给每个节点补边”。

上次本体图修复为**已有业务关系**生成类型声明并修正显示；原始业务事实保持不变，
因此不可能同时恢复本轮发现的未抽取关系。显示缺陷与抽取覆盖缺口需要分别处理。

## 官方文档确认

| 机制 | 官方依据与边界 |
| --- | --- |
| 按领域语义建模 | [Ontology design: Best practices](https://www.palantir.com/docs/foundry/ontology/ontology-best-practices) 要求对象表示有意义的现实概念，模型服务于业务理解，避免照搬源数据结构。不能把“识别了所有名词”直接视为完成领域建模。 |
| 对象与属性有区别 | [Types reference](https://www.palantir.com/docs/foundry/object-link-types/type-reference) 区分对象类型、对象特征属性和连接对象的关系类型。文档没有规定本文三个采购类别必须建对象或必须降为属性。 |
| 关系定义与关系数据都要存在 | [Link types](https://www.palantir.com/docs/foundry/object-link-types/link-types-overview) 区分类型定义和对象间的实际链接；[Create a link type](https://www.palantir.com/docs/foundry/object-link-types/create-link-type) 说明外键、关联表和 backing object 三种数据映射方式。创建关联表的结构不等于已获得业务关系数据。 |
| 关系应有独立含义 | [Structural guidance](https://www.palantir.com/docs/foundry/ontology/ontology-structural-guidance#links-and-object-backed-link-types) 要求每种关系回答明确的领域问题。关系携带日期、角色或状态时，使用 object-backed link 承载元数据；应用可展示直接连接或中间对象。 |
| 图探索沿已有链接展开 | [Vertex: Explore object relationships](https://www.palantir.com/docs/foundry/vertex/explore-object-relationships) 允许先添加对象，再通过 Search Around 选择链接、筛选及扩展相关对象。这个交互说明如何遍历关系，不是从名词共现生成关系的机制。 |
| 以业务问题验证可用性 | [Ontology design: Validation](https://www.palantir.com/docs/foundry/ontology/ontology-design-validation) 将无法在相关概念之间移动列为检查缺失、误命名、方向错误或不可用链接的信号；要求区别模型、数据、权限和应用问题。结构检查不能代替实际任务验证。 |
| LLM 可以单独复核和评估 | [AIP Logic blocks](https://www.palantir.com/docs/foundry/logic/blocks) 可串联多个 LLM/函数步骤；[AIP Evals](https://www.palantir.com/docs/foundry/aip-evals/overview) 支持用例、模型/提示词比较和多次运行检查。[Create an evaluation suite](https://www.palantir.com/docs/foundry/aip-evals/create-suite) 提供 LLM-as-a-judge 评估器，但评估标准仍需明确配置。 |

## 本项目的推断与适配建议

以下是基于公开机制的项目适配，不是 Palantir 对采购制度的既定本体或内部提示词。
后续授权实施及真实模型验证记录见文末；操作说明见
[独立语义覆盖复核](../candidate-semantic-coverage.md)。

### 1. 先确认类别的角色

“办公设备”“软件服务”在本文是采购资源类别。若需要按类别独立检索、复用和导航，
可以保留类别对象，并表达其与采购申请/采购活动的适用范围关系。若只需要作为申请的
描述性取值，可以选择属性表示。具体选择由业务目标和 LLM 的来源支持分析决定；
不能按字符串或节点度数自动重分类、删除或合并。

就当前已授权的图浏览方式，优先复核既有类别节点的来源支持关系，避免先做大范围模型迁移。
“采购申请 → 适用的采购类别 → 办公设备/软件服务/其他业务资源”仅是便于讨论的候选
表达；具体谓词、方向、限定条件及最终是否采用，应由 LLM 结合原文输出并接受校验。

### 2. 保留条件与多参与方含义

资源类别出现在条件中，不表示员工已经购买了相应资源，也不表示一次申请同时采购全部类别。
紧急原因中的“或”也不能改成全部同时必需，更不能把单个原因单独当成充分条件。

含条件、模态、时限和引用的关系可借鉴 object-backed link 的设计思想。本项目已有
qualified RDF statements，应先检查它们能否承载 LLM 明确输出的关系及限定条件引用，
而不是用代码创建定制审批规则类。语义来自模型；代码只进行通用约束校验和标准表示转换。

### 3. 在 LLM 链路增加独立覆盖复核

本例提示词已有覆盖要求，继续堆叠相同指令无法证明问题解决。可增加独立的 LLM 复核步骤：

1. 输入原文、实体、候选关系及完整限定条件，按句检查参与方、对象、范围、条件和时限。
2. 对每个尚未关联的实体给出有证据的处置：已有结构化关联、仅存于限定条件文本、缺少
   受支持关联、仅描述性取值、或证据不足；不能默认全部都要连边。
3. 由 LLM 输出所需修订、原文依据和保留的限定条件，再由代码验证 ID、证据定位、
   输出覆盖及内部一致性。语义复核结论仍是模型候选结果，不是事实真值证明。
4. 不在代码中硬编码 `办公设备 → 采购申请` 或根据词共现、度数为零、同一引用自动连边。
5. 保留抽取、复核、修订的原始响应，便于比较、审阅和离线重放。

### 4. 采用任务驱动的评估

通过 LLM 语义评估检查以下问题能否从结构化结果回答，而不只是回读证据文本：

- 哪些采购类别适用提前提交采购申请的要求？
- 谁向谁申请什么授权，其适用条件是什么？
- 紧急原因与无法提前审批的完整条件如何关联？
- 补齐材料的义务发生在何种活动之后，期限和模态是什么？

通用结构检查可报告未关联节点、缺少端点或证据问题；不能以“所有节点度数必须大于零”
作为正确性标准。评估用例是质量检查，不是运行时生成业务关系的规则库。

## 授权实施与真实模型验证（2026-09-21）

新增 `semantica/semantic_extract/candidate_coverage.py`。CLI 在原生实体、关系抽取后，
调用独立模型复核；也可用 `--review-bundle` 复核既有原始抽取。随后仍通过 LLM 生成
对应业务本体，使用标准 qualified RDF 表示保存断言，再通过原有 LLM 溯源链路生成
业务及证据关系声明。原始响应、复核响应、输入/提示词哈希及逐项审计分别留档。

代码仅校验唯一 ID、端点、原文定位、审计覆盖、引用一致性，以及被标记为“保留”的
断言是否原样复制。不按孤点、关键词、共享证据或同句共现生成业务边。

### 实验揭示的限制

第一版独立复核（`candidate-semantic-coverage-v1`）在真实 DeepSeek 调用中保留了全部
21 条原关系，把 9 个孤点都标为 `descriptive`，理由主要是“只在原来的条件字符串中”
或“已有动作连到了接收人”。输出通过了结构校验，但没有解决类别范围和多参与方覆盖。
该结果留作失败案例，没有加载到运行中的 Explorer。

这说明增加一次 LLM 调用或检查节点/条款审计数量，仍不足以证明模型正确覆盖了原文。
“只在旧模型的条件文本中”是在描述旧输出，不是原文不支持关联的依据；
“受条件限定的关系”也不能等同于“没有可独立表达的关系”。

第二版（`candidate-semantic-coverage-v2`）加入来源驱动的任务问题及回答审计：由模型
检查类别范围、谁向谁申请什么、例外的完整条件、前后时序和补充义务等实际存在的问题。
每个回答列出实体 ID、最终关系 ID、条件和证据。程序只验证引用的实体确实出现在
这些关系的端点中；问题选择与语义判断仍由模型完成，不能确认时记录 `unresolved`。
旧 v1 复核记录保留原提示词哈希与响应结构，可原样离线重放，不自动添加 v2 评估。

v2 的真实响应还暴露了两类问题：一是把原来两个证据行范围合并后仍声称“保留”，
被严格校验拒绝，完整响应写入 `coverage-rejected.json`；二是模型仍会把接收人移入
条件文本、忽略“还需要”指代的前序审批参与者。失败产物没有发布。

因此 v3 在不改变结构校验的前提下，加入通用的条件范围、多参与方请求和相对时序
示例，说明 qualified link 的表达能力，并要求任务回答列出所有已抽取的相关指代对象。
它同时明确跨句承接和“保留”证据数组逐项相同的要求。这些是项目提示词的示例指导，
不是运行时业务规则或要求模型照抄的固定谓词。v1/v2 提示词和响应契约继续独立重放。

第一轮未获得可用结果的调用没有发布产物；随后带响应状态记录的调用使用
`deepseek-v4-flash`，将输出额度设为 32000。额度仅影响可返回长度，不决定语义验收。

### 运行参数核查

另于 2026-09-21 核查 [DeepSeek Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)
及 [Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/)。
官方文档说明思考模式默认开启、默认强度为 `high`，可显式设置 `reasoning_effort`；
思考模式下 `temperature` 不起作用，因此不能把配置为 0 当作重复生成完全相同结果的保证。

本地长请求在约 5 分钟后没有返回标准 completion。代码增加了可选
`reasoning_effort` 的透传（实体/关系/覆盖复核、本体调用和 OpenAI 兼容请求），
不按业务内容选择参数，也不改变未设置该参数的调用。此次随后尝试 `low` 和
32000 的输出额度，仍执行相同的严格校验。网关实际支持的模型与参数须单独验证，
不能从 DeepSeek 官方模型目录推断企业网关全部可用。

### 当前实施：分阶段限制输出

用户明确要求避免单次模型输出过大后，默认入口改为
`candidate_coverage_stages.py` 的 `candidate-semantic-coverage-staged-v4`：

| 阶段 | 模型职责 | 单次 completion 上限 |
| --- | --- | --- |
| 诊断 | 从原文提出可回答的问题，明确所需实体及覆盖差异 | 6000 token |
| 增量修订 | 只输出保留 ID、替换、移除和新增；不重抄保留关系 | 10000 token |
| 独立验收 | 对最终关系审计实体、条款和任务回答，决定通过或继续修订 | 12000 token |

调用方设置更小预算时取较小值。每个技术失败阶段最多重试一次，反馈中保留失败响应和
具体校验错误；语义验收最多触发第二轮修订。失败不覆盖运行中的 Explorer。
各阶段分别保存提示词、模型响应及哈希，支持离线重放；Python 接口可复用已验证阶段，
从尚未完成的调用继续，但不能借恢复运行重置重试限额。

这借鉴 AIP Logic 的多步骤组合和 AIP Evals 的独立评估机制；三个阶段的具体划分、
JSON 契约、预算和重试次数是本项目实现，并非 Palantir 固定配置。

真实试验表明，单体 v3 复核虽生成 31 条关系，但一次 completion 达到 24857 token
（包括 13938 reasoning token），因此不作为当前默认方案。分阶段后，保留项通过原
ID 引用，修订和验收不用重复完整关系列表。`thinking=disabled` 的响应明显缩小，
却出现限定条件丢失、遗漏请求对象，以及 `needs_revision` 与“无需修复”相矛盾的结果。
这些是模型质量问题，不能靠缩短输出或通过 JSON 校验就视为解决。

一次启用低强度思考的分阶段试验生成了 27 条关系，诊断/修订 completion 分别为
2758/3299 token。虽然三个资源类别已有关联，独立审计仍以“当前没有边”为由排除
部分实体。因此最新版诊断要求**逐实体纳入问题或给出有原文依据的非问题解释**；
代码只验证处置覆盖和引用，不要求全部连边。提示词也明确已有多条关系可共同表达
并列要求，不应凭空增加组合关系。以下最终验证与这些实验产物分别留档。

### 分阶段 v4 的真实材料验证

本地 `.local/candidate-profile-v3-coverage-staged7/` 使用同一份原文和原始实体，
由 `deepseek-v4-flash` 完成诊断、增量修订及独立验收，无阶段重试。
运行参数为 `reasoning_effort=low`、`thinking.type=enabled`，各阶段受上述上限约束。

| 调用 | Completion（含思考） | Reasoning | 非思考部分 | 耗时 |
| --- | ---: | ---: | ---: | ---: |
| 诊断 | 3973 | 2966 | 1007 | 39.7 秒 |
| 增量修订 | 4116 | 2812 | 1304 | 43.4 秒 |
| 独立验收 | 7920 | 4299 | 3621 | 76.6 秒 |

非思考部分按网关返回的 completion 与 reasoning token 数之差计算。
随后业务本体生成另一次调用为 4243 completion token（含 2290 reasoning），42.5 秒。
仅保存响应正文及用量元数据，没有导出模型隐藏思考内容。

22 个实体、原文及来源标识保持不变；模型明确保留 21 条原关系，新增 10 条，形成
31 条候选关系。三个资源类别均通过 `采购申请 → involves → 资源类别` 关联，并带
“因业务需要采购”的限定及第 10–11 行引用。其余新增候选涉及授权请求对象、紧急
原因/流程和补齐材料的相对时序。谓词、方向、条件均来自保存的模型补丁。

模型独立验收覆盖 22 个实体、14 组条款和 9 个任务问题，结论为 `pass`、无 unresolved。
这一批恰好没有孤立业务实体，不作为今后要求所有实体都有连线的规则。
原始审批关系及跨句承接引用原样保留，原有采购类别“或”条件、紧急复合条件、
“可以”许可和“3 个工作日内必须补齐”断言仍在。所有内容仍标记为候选、未人工审核。

离线重放验证了事实、原始模型记录和阶段提示词一致，RDF 图同构；qualified RDF
保留检查和业务 SHACL 校验通过。相关后端回归为 673 项通过；两项要求 Windows
符号链接权限的测试在当前环境排除。不能将这些结构验证当成业务真值证明。

### 本体声明及浏览器验收

业务事实通过后，旧 v4 声明提示词仍包含大量重复记录。启用思考的调用达到 12000
completion 上限后截断；关闭思考的调用虽只输出 3475 token，却重复拆分多目标类型的
同一路径声明，并遗漏部分证据类型声明，均被校验拒绝，没有加载到 Explorer。

因此声明提示词更新为 `candidate-provenance-model-v5`：按显式来源类型/路径整理
